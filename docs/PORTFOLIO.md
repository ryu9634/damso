## 1. 무엇을 만들었나

혼술바에서 진행하는 **오프라인 소개팅 이벤트**의 처음부터 끝까지를 소프트웨어로 옮겼다.

사장님은 종이와 엑셀로 손님을 짝지어 앉히고 있었다. 18명(9남 9여)이 네 번 자리를 바꾸는 동안
"누구를 누구 옆에 앉힐지"를 매번 손으로 계산하는 일은 느리고, 일관성이 없고, 무엇보다 재미가 없었다.
이걸 **알고리즘 문제로 바꿔서 자동화**한 게 이 프로젝트의 출발점이다.

이후 요구가 늘면서 세 개의 제품이 한 서비스 안에 들어왔다.

| 영역 | 하는 일 |
|---|---|
| **매칭 이벤트** | 현장 7단계 진행 — 등록 → 1~4차 자리 배치 → 호감도 지목 → 메시지 → 종료 |
| **셀렉팅** | 상시 운영 소개팅. 프로필·좋아요·쌍방 매칭·약속 잡기·웹 푸시 |
| **게임방 / 매장 앱** | 방 코드로 모여 하는 게임 4종, 매장 캘린더, 방명록, 주류 메뉴 |

사용자는 세 종류다. **손님 휴대폰**(QR 입장, 로그인 불필요), **회원 앱**(가입·소셜 로그인),
**관리자 PC**(이벤트 진행·회원 심사·통계). 화면과 권한이 셋 다 다르다.

## 2. 핵심 — 자리 배치를 이분 그래프 매칭으로

📄 [`SeatAssignmentService.java`](../backend/src/main/java/com/damso/match/domain/event/service/SeatAssignmentService.java)

### 문제 정형화

"남녀를 궁합 좋은 순으로 옆자리에 앉힌다"는 요구는 고전적인 **할당 문제(Assignment Problem)** 다.

- 남성 N명 × 여성 M명을 노드로, 각 쌍의 궁합 점수를 간선 가중치로 두면
  **이분 그래프 최대 가중치 매칭(maximum weight bipartite matching)**
- 좌석이 최대 9석(n ≤ 9)이므로 **순열 완전탐색(Heap's algorithm)** 으로 근사가 아닌 **정확한 최적해**를 보장

헝가리안 알고리즘 O(n³)을 쓸 수도 있었지만 쓰지 않았다.
9! = 362,880 은 수 ms에 끝난다. **Big-O가 아니라 실제 문제 크기에 맞는 도구를 골랐다.**
대신 나중에 좌석이 늘어나도 갈아끼울 수 있도록, 탐색부를 `bestAssignment()` 하나로 격리했다.

### 회차마다 전략을 바꾸는 하나의 엔진

점수 행렬 구성만 회차별로 바꾸고 **탐색 코어는 공유**한다.

| 회차 | 전략 |
|---|---|
| 1차 | 손님이 입력한 자리 그대로 |
| 2차 | 궁합 점수 **최대화** — 잘 맞는 사람과 앉아본다 |
| 3차 | 궁합 점수 **최소화** — 2차와 같은 계산에서 **부호만 뒤집는다** |
| 4차 | 호감도 **상호 지목 티어** 우선 |

3차가 이 프로젝트에서 가장 마음에 드는 결정이다.
"점수가 잘 맞는 사람과 앉는 자리가 있으면 반대도 있어야 재밌다"는 기획 아이디어를,
**이미 있는 코드의 부호 하나를 뒤집어** 구현했다. 점수는 점수일 뿐이고 만나보면 다르다는 것이
이 서비스가 하려는 이야기이기도 하다.

### 제약을 "점수 하나"로 표현하기

여러 종류의 제약을 별도 분기 없이 전부 가중치에 녹였다.

| 요구사항 | 구현 |
|---|---|
| 이전 회차에 앉았던 자리 회피 | 해당 조합에 `-1e15` 페널티 (소프트 제약) |
| 동점일 때 늘 같은 답이 나오는 문제 | `rand.nextDouble() * 0.001` 미세 노이즈로 타이브레이킹 |
| 쌍방 1순위는 무조건 옆자리 | 회피 페널티보다 우선하도록 티어 4만 예외 처리 |
| UI상 자리 1~6과 7~9의 성별 슬롯이 반전 | `maleSlot()/femaleSlot()` 으로 로직에 흡수 |

**상호 지목 우선순위는 지수 가중치로 사전식 순서를 만들었다.**

| 티어 | 관계 | 가중치 |
|---|---|---|
| 4 | 쌍방 1순위 | 1000³ |
| 3 | 1·2순위 교차 / 쌍방 2순위 | 1000² |
| 2 | 단방 지목 | 1000¹ |
| 1 | 미지목 | 1000⁰ |

```java
double base = Math.pow(1000.0, tier - 1);
```

간격이 1000배라서 **상위 티어 1쌍이 하위 티어 몇 쌍을 합쳐도 무조건 이긴다.**
"쌍방 1순위를 먼저 붙이고, 그 다음 교차를 붙이고…" 같은 다단계 정렬을
**점수 하나로 표현**해서 탐색 코어를 건드리지 않았다.

### 성비가 안 맞을 때 — 가상 열 패딩

남성이 여성보다 많으면 짝 없는 남성이 생긴다. 처음엔 여성 수만큼만 순열을 돌렸는데,
그러면 **뒤쪽 인덱스의 남성은 점수와 무관하게 늘 미배치**가 됐다. 궁합이 가장 좋은 남성이
등록 순서가 늦다는 이유로 옆자리를 놓치는 버그였다.

정사각 행렬로 패딩해서 해결했다.

```java
// 남성이 여성보다 많으면 '짝 없음'을 뜻하는 가상 열을 채워 정사각으로 만든다.
// 가상 열은 어떤 순열에서도 정확히 (nMales - nFemales) 개가 쓰이므로 총점 비교에 영향이 없다.
int n = Math.max(nMales, nFemales);
```

**"짝 없음"도 선택지의 하나로 만들면 탐색이 알아서 최적을 찾는다.** 예외 분기가 사라졌다.

### 테스트 — 구현이 아니라 성질을 검증한다

📄 [`SeatAssignmentServiceTest.java`](../backend/src/test/java/com/damso/match/domain/event/service/SeatAssignmentServiceTest.java)

탐색 알고리즘 테스트는 구현을 그대로 베끼기 쉽다. 그러면 구현이 틀렸을 때 테스트도 같이 틀린다.
그래서 **테스트가 독립적으로 브루트포스 오라클을 구현하고, 서비스 결과의 원점수 합이
그 최적값과 같은지만 확인**한다.

- 구현을 흉내 내지 않으므로, 나중에 헝가리안으로 바꿔도 **테스트는 그대로 유효**하다
- 서비스가 더하는 미세 노이즈에 흔들리지 않도록 테스트 점수는 항상 10 단위로 벌린다

## 3. 궁합 점수 엔진 — 매칭의 입력값

📄 [`MatchScoreService.java`](../backend/src/main/java/com/damso/match/domain/dating/service/MatchScoreService.java)

앞의 탐색 알고리즘이 최적화하는 **간선 가중치**를 만드는 곳이다. 100점 만점.

| 항목 | 배점 | 방식 |
|---|---|---|
| MBTI 궁합 | 20점 | 직접 설계한 **16×16 매트릭스** (0=최악 / 10=반반 / 20=천생연분) |
| 가치관 일치 | 80점 | 설문 응답을 **비트열로 저장**하고 문자 단위 일치율을 정규화 |

두 가지를 신경 썼다.

- **문항 수가 바뀌어도 배점이 유지된다.** 가치관 점수는 고정 배점이 아니라
  **현재 활성 문항 수에 비례해 80점으로 정규화**한다. 관리자가 질문을 추가·삭제해도
  총점 체계가 흔들리지 않고, 과거 데이터와도 비교 가능하다.
- **미입력을 0점으로 두지 않는다.** MBTI가 없거나 매트릭스에 없는 값이면 중간값(10점)으로 fallback.
  0점을 주면 "MBTI를 안 적은 사람"이 알고리즘상 기피 대상이 되어 늘 구석에 앉는다.

```java
public int totalScore(Customer a, Customer b) {
    return mbtiScore(a.getMbti(), b.getMbti())                        // 0~20
         + valuesScore(a.getValuesAnswers(), b.getValuesAnswers());   // 0~80
}
```

**점수 엔진과 탐색 엔진을 분리**한 덕분에, 3차 회차(궁합 최소화)는 이 값의 부호만 뒤집어 재사용했다.

## 4. 개인정보 암호화 — 조회가 되는 암호화

📄 [`DataCrypto.java`](../backend/src/main/java/com/damso/match/global/security/DataCrypto.java) ·
[`EncryptedStringConverter.java`](../backend/src/main/java/com/damso/match/global/security/EncryptedStringConverter.java)

실명·휴대폰번호·연락처를 다루는 서비스라 **DB 덤프가 새어도 바로 읽히지 않아야** 했다.
AES-256-GCM으로 컬럼 암호화를 넣었는데, 여기서 진짜 문제는 암호화 자체가 아니라
**"암호화하면 `findByPhone()` 이 안 된다"** 는 것이었다.

### 결정적 암호화 — 트레이드오프를 알고 선택했다

IV를 무작위로 뽑으면 같은 번호도 매번 다른 암호문이 되어 등호 조회가 깨진다.
**IV를 평문의 HMAC으로 유도**해서 같은 평문이 항상 같은 암호문이 되게 했다.

```
IV = HMAC(macKey, plaintext)[0:12]
```

- ✅ `findByPhone(...)` 이 그대로 동작한다 — 파라미터도 같은 규칙으로 암호화되므로 맞아떨어진다
- ⚠️ **"두 행의 번호가 같다"는 사실은 암호문만 봐도 드러난다**

이 단점은 문서에 명시하고 감수했다. 우리 데이터에서 "같은 번호를 쓰는 두 회원"이 노출돼도
잃을 게 없고, 반대로 등호 조회를 포기하면 중복 가입 차단이 불가능해진다.
암호화 키와 IV 유도 키는 마스터 키에서 HMAC으로 분리해 **한 키를 두 용도로 쓰지 않았다.**

### 애플리케이션 코드는 한 줄도 안 바꿨다

JPA `AttributeConverter`로 넣어서 엔티티 필드에 애노테이션만 붙이면 끝이다.
서비스·컨트롤러·화면은 계속 평문만 다룬다.

### 무중단 이관

이미 평문으로 쌓인 데이터가 있었다. 부팅 시 마이그레이션이 돈다.

- 접두어 `enc1:` **가 없는 행만** 고르므로 **몇 번 돌려도 결과가 같다(멱등)**
- 컨버터는 접두어 없는 값을 그대로 반환 → **이관 도중에도 화면이 깨지지 않는다**
- **실패하면 애플리케이션이 뜨지 않는다** — 평문이 조용히 남는 것보다 배포가 되돌아가는 게 낫다

키는 배포 디렉터리 **바깥**(`/var/lib/damso/damso.key`)에 둬서 릴리스 교체에 살아남고,
백업 스크립트가 함께 보관한다. 비밀번호는 애초에 대상이 아니다 — 되돌릴 필요가 없으니 BCrypt 해시다.

## 5. 배포 — 서버에 22번 포트를 열지 않는다

> 운영 중지와 함께 배포 스크립트·워크플로는 저장소에서 제거했다. 아래는 운영 당시의 기록이다.

처음엔 GitHub Actions에서 SSH로 접속하는 흔한 방식이었다. 이걸 걷어냈다.

```
git push main
  → GitHub Actions: 프론트 빌드 → 테스트 → jar 빌드 → jar 안에 프론트가 들어갔는지 검증
  → AWS OIDC 로그인 (액세스 키 없음)
  → jar 을 S3 업로드
  → SSM RunShellScript 로 서버에 배포 명령 전달
  → 서버: 릴리스 배치 → 심볼릭 링크 교체 → 재시작 → 헬스체크
      실패하면 이전 릴리스로 자동 롤백하고 0이 아닌 코드로 종료
```

### 이 구조에서 얻은 것

| 결정 | 이유 |
|---|---|
| **SSH 제거, SSM 사용** | 서버가 **인바운드 포트를 하나도 열지 않는다.** SSM은 서버가 밖으로 거는 연결만 쓴다 |
| **OIDC 인증** | 장기 AWS 액세스 키를 GitHub 시크릿에 두지 않는다 |
| **심볼릭 링크 릴리스** | `current` 링크만 바꾸면 되므로 롤백이 링크 되돌리기 한 번 |
| **헬스체크 후 자동 롤백** | **되돌리는 것까지가 배포다.** 헬스체크가 실패했는데 그대로 두면 장애가 남는다 |
| **`concurrency: cancel-in-progress: false`** | 배포가 겹치면 릴리스 링크가 꼬인다. 취소하지 않고 기다린다 |
| **jar 내용물 검증** | `frontend/dist/` 가 없으면 Maven이 조용히 건너뛰고 **프론트 없는 jar**이 나온다. 흰 화면으로 알게 되는 대신 CI에서 멈춘다 |

`provision.sh`는 **멱등**하게 짰다. 여러 번 돌려도 이미 만들어진 건 건드리지 않는다.
서버를 날려도 스크립트 한 번이면 같은 상태가 재현된다.

## 6. 그 외 설계 판단

**인증** 📄 [`AuthService.java`](../backend/src/main/java/com/damso/match/domain/member/service/AuthService.java)
- 세션은 **불투명 토큰**(DB 저장, 90일). JWT를 쓰지 않은 건 관리자가 회원을 즉시 차단·휴면 처리해야 하는데
  자체 만료되는 토큰으로는 그게 안 되기 때문
- 아이디 계정과 카카오/네이버 소셜 계정을 **한 사람으로 병합**할 수 있다. `(provider, providerId)` 유일 제약으로 중복 연결 차단
- 로그인 수단에서 실명·휴대폰번호를 **의도적으로 뺐다** — 개인정보를 인증 키로 쓰지 않는다

**셀렉팅 도메인** 📄 [`DatingService.java`](../backend/src/main/java/com/damso/match/domain/dating/service/DatingService.java) · [`DatingScheduler.java`](../backend/src/main/java/com/damso/match/domain/dating/service/DatingScheduler.java)
- 좋아요 **72시간 자동 만료**를 **스케줄러 + 목록 조회 양쪽**에서 정리한다.
  스케줄러만 있으면 방금 만료된 건이 화면에 남고, 조회 시점 정리만 있으면 아무도 앱을 안 여는 동안 상태가 멈춘다
- **매칭돼도 연락처를 공개하지 않는다.** 약속은 앱 안에서만 잡히고 만남은 매장에서 이뤄진다 — 온라인 소개팅 앱과의 차별점을 제품 정책이자 보안 설계로 세웠다
- **매장 대면 확인 배지** — 관리자가 실제로 얼굴을 본 회원만 켠다. 온라인 앱이 줄 수 없는 보증

**웹 푸시** 📄 [`WebPushService.java`](../backend/src/main/java/com/damso/match/domain/notification/service/WebPushService.java)
- VAPID 서버 키를 첫 실행 때 생성해 설정에 보관, 발송 실패한 죽은 구독은 자동 삭제

**스키마 관리** (운영 당시 — 현재는 PostgreSQL + Flyway 단일 구성)
- 개발은 H2, 운영은 PostgreSQL이라 DDL 방언이 다르다(`SET NULL` vs `DROP NOT NULL`).
  둘 다 시도하고 **양쪽 모두 실패했을 때만** 진짜 실패로 본다
- enum 값이 늘면 기존 CHECK 제약에 걸리므로 부팅 시 제약을 정리하는 마이그레이션을 함께 넣는다

**실시간 동기화**
- WebSocket 없이 **4초 폴링**. 동시 접속 18명 규모에서 WebSocket의 운영 복잡도(연결 유지, 재연결, nginx 설정)를
  감당할 이유가 없었다. 이벤트가 교체되면 세션을 자동 무효화한다

## 7. 트러블슈팅

### 운영에서만, 특정 경로에서만 터진 500

**증상** — 앱에서 소개팅 등록을 누르면 500. 관리자 화면에서 등록하면 정상. 로컬에서도 정상.

**원인** — `CustomerService`는 클래스에 `@Transactional(readOnly = true)`가 걸려 있는데,
앱이 부르는 `create(req, appUserId)` 에만 `@Transactional`이 없었다. 읽기 전용 트랜잭션이
그대로 이어져 **PostgreSQL이 INSERT를 거부**했다(SQLState 25006).

**왜 안 잡혔나** — 인자 하나짜리 `create()`는 쓰기 트랜잭션을 열고 이 메서드를 호출해서 관리자 경로는 멀쩡했고,
**개발용 H2는 읽기 전용을 강제하지 않아** 로컬 테스트도 통과했다.

**대응** — 해당 메서드에 `@Transactional`을 붙이고, **같은 모양(클래스 readOnly + 쓰기 메서드)을 전부 훑어**
나머지는 모두 쓰기 트랜잭션 안에서 불리는 private 헬퍼임을 확인했다.

**배운 것** — 개발/운영 DB가 다르면 **관대한 쪽에서 테스트하는 것이 위험**하다.

---

### 배포가 1초 만에 롤백되던 문제

**증상** — 배포가 매번 "서비스가 기동하지 못했습니다"로 롤백. 그런데 수동 재시작은 정상.

**원인** — `deploy.sh`의 헬스체크가 `sudo systemctl is-active --quiet damso`를 썼는데,
sudoers에 등록된 건 `--quiet` 없는 `systemctl is-active damso`였다. **문자열이 어긋나 sudo가 비밀번호를 물었고,
그 실패가 그대로 "서비스가 죽었다"로 읽혔다.**

**대응** — `is-active`는 조회일 뿐 권한이 필요 없다. **sudo를 떼서 sudoers 문자열과 어긋날 가능성 자체를 없앴다.**

**곁가지 두 개** — 진단이 안 되던 이유도 같이 고쳤다.
`deploy` 계정이 `systemd-journal` 그룹에 없어 실패 시 `journalctl` 출력이 비어 있었고,
S3 전송 진행률 로그(48MB)가 실제 오류를 덮고 있었다(`--no-progress`).

**배운 것** — **장애를 고치기 전에 "왜 원인이 안 보였나"를 먼저 고친다.**

---

### 백업이 조용히 안 돌고 있었다

**증상** — 백업 cron이 등록돼 있는데 결과물이 없었다.

**원인** — `backup.sh`가 환경 파일을 `source`로 읽었다. systemd 환경 파일은 따옴표 없이 값을 쓰는데,
`JAVA_OPTS=-Xmx768m -Xms256m` 같은 줄에서 **공백 뒤가 명령으로 실행**되며 스크립트가 죽었다.

**대응** — systemd 형식을 그대로 해석하는 로더로 교체.

**배운 것** — 조용히 실패하는 배치는 실패하지 않는 것보다 나쁘다. 이후 **백업 결과를 검증하는 단계**를 넣었다.

## 8. 면접에서 이야기할 거리

1. **왜 헝가리안 알고리즘이 아니라 완전탐색인가?**
   n ≤ 9라서 9!가 수 ms에 끝난다. 최적해가 보장되면서 구현이 단순한 쪽을 골랐고,
   나중에 갈아끼울 수 있도록 탐색부를 한 메서드로 격리해뒀다. Big-O는 판단 기준의 일부일 뿐이다.

2. **여러 종류의 제약을 어떻게 분기 없이 처리했나?**
   전부 가중치로 표현했다 — 회피는 `-1e15` 페널티, 동점은 미세 노이즈, 우선순위는 `1000^tier` 지수 가중치.
   다단계 정렬을 점수 하나(사전식 순서)로 접어서 탐색 코어를 건드리지 않았다.

3. **암호화하면 조회가 안 되는 문제를 어떻게 풀었나?**
   IV를 평문의 HMAC으로 유도하는 결정적 암호화. **"같은 값끼리는 같다는 게 드러난다"는 대가를 알고 선택**했고,
   그 이유를 코드 주석에 남겼다.

4. **배포에서 SSH를 왜 걷어냈나?**
   SSM은 서버가 밖으로 거는 연결만 쓰므로 **인바운드를 전부 닫을 수 있다.**
   OIDC까지 붙여서 장기 자격증명도 없앴다.

5. **테스트를 어떻게 짰나?**
   탐색 알고리즘 테스트는 구현을 베끼기 쉽다. 테스트가 독립적인 브루트포스 오라클을 갖고
   **"결과가 최적인가"라는 성질만** 검증한다. 구현을 바꿔도 테스트는 살아남는다.

6. **1인 개발에서 품질을 어떻게 지켰나?**
   CI가 테스트·빌드·**jar 내용물까지** 검증하고, 배포는 헬스체크 실패 시 자동 롤백한다.
   그리고 **커밋 메시지에 "왜"를 남긴다** — 세 달 뒤의 나에게 유일한 문서다.
