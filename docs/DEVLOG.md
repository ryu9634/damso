## 1기 — 현장 도구 만들기 (6월)

**`06-10` 담소 매칭 시스템 초기 커밋**

시작은 단순했다. 매장에서 종이와 엑셀로 하던 자리 배치를 자동화하는 것.

정한 것들:

- **관리자 PC + 손님 휴대폰** 두 화면. 손님은 로그인 없이 QR로 들어온다.
  현장에서 회원가입을 시키면 이벤트가 멈춘다.
- **이벤트를 7단계 상태 머신으로.** 관리자가 버튼으로 단계를 넘기고, 손님 화면은 현재 단계에 맞는 것만 보여준다.
  진행 순서를 코드가 강제하니 사장님이 헷갈릴 일이 없다.
- **H2 파일 DB.** 매장 노트북에서 돌릴 거라 별도 DB 서버를 세울 수 없었다.
  `AUTO_SERVER` + PostgreSQL 호환 모드로 켜서, 나중에 서버로 옮길 길을 열어뒀다.
- **단일 JAR.** 백엔드가 React 빌드 결과물과 업로드 이미지까지 정적 서빙한다.
  배포가 파일 하나 옮기기가 된다.

이 단계에서 자리 배치를 **이분 그래프 최대 가중치 매칭**으로 정형화했다.
n ≤ 9라 완전탐색으로 최적해를 보장할 수 있다는 게 이 프로젝트 전체를 편하게 만든 판단이었다.

> 💡 **회고** — 로컬 전용으로 시작한 건 옳았다. 인프라부터 세웠으면 두 달 뒤에도 첫 이벤트를 못 돌렸을 것이다.

## 2기 — 상시 서비스로 (8월 중순)

**`08-12` 소개팅 회원관리 고도화 + 모바일 사진 등록 개선 → 랜딩 타이틀 '담소 셀렉팅'**

이벤트가 몇 번 돌아가자 요구가 바뀌었다.
"이벤트 날에만 쓰는 도구" 말고 **평소에도 돌아가는 소개팅**이 필요해졌다.

- 회원 프로필·사진을 상시 관리하는 영역이 생겼다 → 이게 **셀렉팅**이 된다
- 모바일에서 사진 등록이 잘 안 됐다. 원인이 세 개였다.
  폰 원본 사진이 3~12MB라 LTE에서 업로드가 오래 걸리고, 서버 업로드 제한(8MB)에 걸리고,
  아이폰 HEIC는 관리자 PC(윈도우 크롬)에서 아예 열리지 않았다.
  **브라우저 캔버스로 다시 그려 JPEG로 내보내니 세 개가 한 번에 해결됐다**(긴 변 1600px, 품질 0.82).
  단, 디코딩에 실패하면 원본을 그대로 올린다 — 압축은 최적화일 뿐이라 등록을 막을 이유가 없다

> 💡 **회고** — 여기서 프로젝트 성격이 바뀌었다. "현장 도구"에서 "서비스"로.
> 이때부터 **인증·배포·개인정보**가 전부 숙제가 됐다.

## 3기 — 서비스가 되기 위한 것들 (8/23)

**`08-23` 앱 회원·관리자 인증 · 운영 배포용 설정 분리 → 배포 파이프라인 (VPS + PostgreSQL + nginx)**

상시 서비스가 되려면 **로그인**과 **서버**가 있어야 했다. 하루에 둘 다 붙였다.

**인증에서 고민한 것**

- **JWT를 쓰지 않았다.** 관리자가 회원을 즉시 차단·휴면 처리해야 하는데,
  자체 만료되는 토큰으로는 "지금 당장 끊기"가 안 된다. DB에 저장하는 **불투명 토큰**(90일)으로 갔다.
- **로그인 수단에서 실명·휴대폰번호를 뺐다.** 개인정보를 인증 키로 쓰지 않는다.
  아이디 + 비밀번호(BCrypt)만 쓰고, 카카오/네이버는 별도 링크 테이블로 계정에 붙인다.
- 아이디 계정과 소셜 계정이 한 사람이면 마이페이지에서 **병합**할 수 있게 했다.
  `(provider, providerId)` 유일 제약으로 중복 연결을 막는다.

**배포에서 정한 것**

- 개발은 H2, 운영은 PostgreSQL. 데이터 이관 스크립트를 같이 만들었다
- `provision.sh`를 **멱등**하게 짰다. 여러 번 돌려도 안전하고, 서버를 날려도 한 번에 재현된다
- systemd + nginx + 릴리스 심볼릭 링크

> 💡 **회고** — 배포 스크립트에 처음부터 **롤백**을 넣은 게 나중에 몇 번을 살렸다.
> "되돌리는 것까지가 배포다"라는 문장을 스크립트 주석에 적어뒀다.

## 4기 — AWS 전환과 기능 폭증 (8/27, 하루)

**`08-27` — 하루에 커밋 6개**

이날 두 가지가 동시에 일어났다. 인프라를 갈아엎었고, 기능 요구가 쏟아졌다.

### AWS 배포로 전환 — SSH를 걷어내다

VPS + SSH 배포가 4일 만에 마음에 안 들어졌다. **서버에 22번 포트가 열려 있다**는 게 계속 걸렸다.

```
S3 에 jar 업로드 → SSM RunShellScript 로 배포 명령 전달
```

- SSM은 **서버가 밖으로 거는 연결만** 쓴다 → 인바운드를 전부 닫을 수 있다
- GitHub Actions는 **OIDC**로 AWS에 로그인한다 → 장기 액세스 키를 시크릿에 두지 않는다

### 그리고 같은 날, 배포가 매번 롤백됐다

**`08-27` 헬스체크가 sudo 때문에 서비스를 죽었다고 오판하던 문제 수정**

배포는 성공하는데 헬스체크가 1초 만에 실패하고 롤백됐다. 수동 재시작은 멀쩡했다.

원인은 **sudoers 문자열 불일치**였다. 스크립트는 `sudo systemctl is-active --quiet damso`를 쓰는데
sudoers에 등록된 건 `--quiet` 없는 버전. sudo가 비밀번호를 묻고 실패했고,
그 실패가 그대로 "서비스가 죽었다"로 읽혔다.

`is-active`는 조회일 뿐 권한이 필요 없다. **sudo를 떼서 어긋날 가능성 자체를 없앴다.**

진단이 왜 안 됐는지도 같이 고쳤다:
- `deploy` 계정이 `systemd-journal` 그룹에 없어 `journalctl` 출력이 비어 있었다
- S3 전송 진행률 로그(48MB)가 실제 오류를 덮고 있었다 → `--no-progress`

> 💡 **회고** — 이날 배운 게 제일 크다. **장애를 고치기 전에 "왜 원인이 안 보였나"를 먼저 고친다.**
> 로그가 안 보이는 상태로 디버깅하면 시간이 몇 배로 든다.

### 같은 날 들어간 기능들

- **회원 휴대폰번호 필수화 · 기능 on/off 스위치 · 좋아요 응답과 만남 약속**
  — 기능 토글을 넣은 건 사장님이 "이번 달은 셀렉팅 쉬어요" 같은 요구를 하기 때문. 배포 없이 껐다 켠다
- **가게 캘린더(행사·휴일)** — 손님이 제일 많이 묻는 게 "오늘 여나요"였다
- **관리자 회원 수정·비밀번호 초기화** — 매장에서 즉시 처리해야 하는 일
- **저장된 비밀번호로 로그인이 안 되던 문제 수정**
- **심사중·휴면·제외 상태에서는 셀렉팅 이용 불가** — 상태 머신을 권한에 연결

## 6기 — 개인정보와 안정화 (9/5~9/9)

### 개인정보 암호화 `09-05`

실명·휴대폰번호·연락처가 평문으로 쌓이고 있었다. **DB 덤프가 새면 그대로 읽힌다.**

AES-256-GCM 컬럼 암호화를 넣었는데, 진짜 문제는 암호화가 아니라
**"암호화하면 `findByPhone()` 이 안 된다"** 였다.

**결정적 암호화**로 풀었다. IV를 무작위로 뽑지 않고 **평문의 HMAC에서 유도**한다.

- ✅ 같은 평문 → 같은 암호문 → 등호 조회가 그대로 동작 (중복 가입 차단, 이름+연락처로 프로필 찾기)
- ⚠️ "두 행의 번호가 같다"는 사실은 암호문만 봐도 드러난다

**단점을 알고 골랐고, 그 이유를 코드 주석에 남겼다.**
등호 조회를 포기하면 중복 가입을 못 막는데, 우리 데이터에서 "같은 번호 쓰는 두 회원"이 드러나도 잃을 게 없다.

나머지 결정들:
- **JPA `AttributeConverter`** — 엔티티에 애노테이션만 붙이면 되고, 서비스·화면 코드는 안 바꿨다
- **부팅 시 자동 이관** — 접두어 `enc1:` 없는 행만 고르므로 **멱등**. 이관 중에도 화면이 안 깨진다
- **실패하면 앱이 뜨지 않는다** — 평문이 조용히 남는 것보다 배포가 되돌아가는 게 낫다
- **키는 배포 디렉터리 바깥**(`/var/lib/damso/damso.key`) — 릴리스 교체에 살아남는다. 백업이 함께 보관
- 비밀번호는 대상이 아니다 — 되돌릴 필요가 없으니 BCrypt 해시 그대로

### 백업이 조용히 안 돌고 있었다 `09-05`

암호화 키를 백업에 넣으려다 발견했다. **백업 cron이 등록돼 있는데 결과물이 없었다.**

`backup.sh`가 환경 파일을 `source`로 읽는데, systemd 환경 파일은 따옴표를 안 쓴다.
`JAVA_OPTS=-Xmx768m -Xms256m` 에서 **공백 뒤가 명령으로 실행**되며 스크립트가 죽고 있었다.
systemd 형식을 그대로 해석하는 로더로 교체했다.

> 💡 **회고** — 조용히 실패하는 배치는 실패하지 않는 것보다 나쁘다.
> "돌고 있다"고 믿고 있던 몇 주가 통째로 백업이 없는 기간이었다.

### 마무리 손질 `09-05~09-06`

- 홈에 '진행 중인 담소 소개팅' 영역 — 로그인 회원이 바로 참여
- 간편로그인 가입에 닉네임을 자동으로 붙이지 않는다 (카카오 닉네임이 그대로 노출되던 문제)
- 셀렉팅을 꺼두면 마이페이지에서도 감춘다 — 기능 토글이 **모든 진입점**을 막아야 한다

### 운영에서만 터진 500 `09-06`

**앱에서 소개팅 등록을 누르면 500. 관리자 화면은 정상. 로컬도 정상.**

`CustomerService`는 클래스에 `readOnly = true`가 걸려 있는데,
앱이 부르는 `create(req, appUserId)` 에만 `@Transactional`이 없었다.
읽기 전용 트랜잭션이 이어져 **PostgreSQL이 INSERT를 거부**했다(SQLState 25006).

**왜 안 잡혔나:**
- 인자 하나짜리 `create()`는 쓰기 트랜잭션을 열고 이걸 호출한다 → 관리자 경로는 멀쩡
- **개발용 H2는 읽기 전용을 강제하지 않는다** → 로컬 테스트 통과

같은 모양(클래스 readOnly + 쓰기 메서드)을 **전부 훑어서** 나머지는 문제없음을 확인했다.

> 💡 **회고** — 개발과 운영의 DB가 다르면 **관대한 쪽에서 테스트하는 게 위험**하다.
> H2가 "괜찮다"고 한 걸 PostgreSQL이 거부했다.

## 지금 하고 있는 것

**좌석 배치 테스트 작성** (`backend/src/test/`)

CI에 `mvn test`가 이미 들어가 있는데 정작 검증할 테스트가 없었다.
매칭 엔진부터 채우는 중이다.

전략: **테스트가 독립적으로 브루트포스 오라클을 구현하고,
서비스 결과의 원점수 합이 그 최적값과 같은지만 확인**한다.
구현을 흉내 내지 않으므로 나중에 헝가리안으로 바꿔도 테스트는 그대로 유효하다.

**성비 불균형 버그 수정** (`SeatAssignmentService`)

테스트를 짜다가 찾았다. 남성이 여성보다 많을 때 여성 수만큼만 순열을 돌려서,
**뒤쪽 인덱스의 남성은 점수와 무관하게 늘 미배치**가 됐다.
궁합이 가장 좋은 남성이 등록 순서가 늦다는 이유로 옆자리를 놓치고 있었다.

**"짝 없음"을 뜻하는 가상 열로 정사각 패딩**해서 해결했다.
짝 없음도 선택지의 하나가 되면 탐색이 알아서 최적을 찾는다. 예외 분기가 사라졌다.

> 테스트를 쓰자마자 버그가 나온 게 딱 그 이유였다.
